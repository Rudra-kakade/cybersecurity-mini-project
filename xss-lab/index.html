Understanding Stored Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is a client-side code injection vulnerability ranked in the OWASP Top 10. It allows attackers to inject malicious scripts into web pages viewed by other users.

When a browser renders a page, it cannot distinguish between legitimate scripts and injected ones embedded in user-supplied content. This trust gap is what XSS exploits. The core principle: untrusted user input is included in output without proper encoding, causing the browser to execute it as code.

Stored XSS is the most dangerous variant — the payload is saved permanently in the database and executes for every visitor who views the infected page. Unlike Reflected XSS (which requires clicking a crafted URL), Stored XSS requires no further interaction from the attacker after initial injection.

In this lab, we use innerHTML (vulnerable) vs textContent (secure) to demonstrate the attack and its fix. Use the comment section below and the Attack Panel on the right to explore different XSS vectors.

📖 Attack Flow
1
Attacker submits a comment containing a malicious script payload (e.g. <img src=x onerror="alert()">).
2
Server stores the raw, unsanitized input in the database — no validation, no encoding.
3
Victim visits the blog post. The server retrieves all comments from the database.
4
Browser renders comments using innerHTML, which parses and executes any HTML/JS in the content.
5
XSS fires! The injected script executes in the victim's browser context — stealing cookies, session tokens, or displaying fake content.
🔧 Vulnerable vs Secure Code
❌ Vulnerable
bodyDiv.innerHTML = comment.body;
// User input parsed as HTML — scripts execute!
✅ Secure
bodyDiv.textContent = comment.body;
// Everything treated as plain text — safe!
